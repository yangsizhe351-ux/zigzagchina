# ZigZag China Worktree 协作架构

## 为什么不固定六个窗口

当前网站的核心源代码只有少量高耦合文件。六个编码窗口会让多人同时改 `src/main.jsx`、`src/styles.css` 和 `src/content.js`，合并成本会超过并行收益。因此采用“总控 + 两个常驻编码窗口 + 按需短任务”的动态架构。

默认并行上限：

1. **总控台（Local）**：保管 `main`、拆任务、合并、回归、更新交接与发布。
2. **平台与 SEO（Worktree）**：处理静态预渲染、真实 404、页面级元数据和构建底座。
3. **视觉与性能（Worktree）**：优化现有图片交付、Logo 资源、字号/触控与响应式；不生成新图。

拿到真实旅游数据后，再按需开启：

4. **产品与内容（Worktree）**：结构化体验数据、询价表、FAQ、政策和真人内容。该窗口替换一个已完成窗口，而不是无限增加并行数。

QA 不长期占一个编码窗口。每次合并前由总控运行完整检查；高风险波次再创建短期只读审查窗口。

## 调度原则

任务同时满足以下条件才进入新的 Worktree：

- 有独立交付物和明确完成标准；
- 主要文件与其他活动窗口不重叠；
- 可以独立验证；
- 不依赖尚未确认的业务数据。

否则留在总控台串行完成，或等待依赖信息。限制在制品数量比追求窗口数量更重要。

## 文件所有权与合并顺序

| 窗口 | 主要所有权 | 当前不应修改 |
| --- | --- | --- |
| 总控台 | 协作文档、共享依赖、最终集成与发布 | 不在工作窗口运行期间重做同一功能 |
| 平台与 SEO | HTML、公开路由、构建/预渲染、404、metadata | 旅行文案、视觉资产、体验交互 |
| 视觉与性能 | CSS、既有图片资源、响应式和加载性能 | 路由架构、产品数据、资质事实 |
| 产品与内容 | 页面交互、结构化内容、询价流程 | 构建平台、未经确认的真实数据 |
| QA（短期） | 检查脚本、测试、审查报告 | 直接修业务代码，除非总控明确转交 |

推荐合并顺序：平台底座 → 产品交互 → 视觉调整 → QA 修正 → 总控发布。若两个提交互不依赖，可由总控根据风险调整顺序，但每合并一个窗口都重新运行检查。

## 每个任务的开场模板

```text
先阅读 AGENTS.md、HANDOFF.md 和 docs/WORKTREE_OPERATING_MODEL.md。
确认当前分支与工作区后，只处理本任务指定范围。
不要部署，不要修改总控专属文件，不要提交 dist-netlify。
完成后提交到当前 Worktree 分支，并回报：提交 SHA、修改文件、验证命令与结果、残余风险、需要总控协调的共享变更。
```

## 总控验收流程

1. 确认工作窗口提交基于当前基线，读取其变更摘要与验证结果。
2. 在 `main` 逐个合并，避免一次混入多个未经验证的主题。
3. 每次合并后运行目标检查；全部合并后运行 `npm run check`、`git diff --check` 和浏览器路由/响应式回归。
4. 更新 `HANDOFF.md`，记录本次 SHA、未完成项和线上状态。
5. 只有用户明确要求上线时，才推送并验证 Netlify；工作窗口永远不直接发布。

## 何时调整窗口数量

- 增加窗口：新任务有独立目录或文件边界，并且不依赖正在变动的接口。
- 减少窗口：两项工作都要改同一个核心文件，或业务数据尚未确定。
- 关闭窗口：任务已经合并、发现前置依赖、或只剩总控可以完成的跨域改动。

这套架构不是固定组织图，而是一个带文件锁、在制品上限和集成闸门的调度方法。
